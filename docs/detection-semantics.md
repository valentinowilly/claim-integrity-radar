# Detection semantics (Claim Integrity Radar)

Status: describes the code in `backend/app/analytics/` as of Phase 5. Every result is a **review signal**, never a fraud finding. No method has been validated against real fraud labels; the official FKRTL sample has none.

## Units and outcome states

| Method | Unit analysed | Output |
|---|---|---|
| Repeat visit (`repeat_billing.py`) | Group of visit records | Exact-match group of ≥ 2 records |
| Similar-claim screening, exploratory (`near_duplicate_claims.py`, code `near_duplicate_claim_candidate`) | Pair of visit records | Candidate pair with matched/differing attribute names |
| ML unusual-claim ranking (`ml_anomaly.py`) | Single visit record | Relative score and competition rank within one run |
| Unusual duration relative to comparable claims, exploratory (`length_of_stay.py`) | Single visit record | Candidate with span, peer support, threshold and median |
| Rule index (`risk_scoring.py`) | Single visit record | Provisional combination of rule checks, or withheld |
| Facility audit priority (`audit_priority.py`) | Facility | Not assessable on FKRTL (no verified facility identifier) |

Every check reports each record as one of: **flagged**, **assessed and not flagged**, **unassessed** (required data missing or the bounded search did not finish the record), or **not applicable** (the source cannot support the check). Unassessed and not-applicable records are never negative findings. Tests: `test_coverage_contract.py`, `test_coverage_correctness.py`.

## Repeat visit

- **Intends to find:** two or more separate visits by the same participant whose key attributes are identical.
- **FKRTL profile (`repeat-service-v1`, applied):** the key is the core definition `repeat_service_v1`: same participant, admission date (FKL03), primary diagnosis (FKL18), INA-CBG (FKL19), procedure (FKL30). Province/district (FKL05/06), facility categories (FKL07–09) and admission diagnosis (FKL16) are compared only as reviewer context: each candidate lists them by field name under `matched_attributes`, `differing_attributes` or `context_unavailable_attributes` (values are never returned). They never decide eligibility or hide a candidate. No amount is used: FKL47 semantics are unconfirmed and FKL48 is post-verification and never read. Synthetic sources keep `repeat-billing-exact-v1`; the former 11-field profile `repeat-visit-exact-no-amount-v1` remains selectable for comparison only. Tests: `test_repeat_service_profile.py`.
- **Missing values:** any missing field makes the record unassessed. **Blank FKL30 meaning is unresolved:** the data dictionary defines FKL30 only as "type of procedure performed"; 41.7% of the 202403 sample is blank. Blank is therefore treated as missing, not as "no procedure". Test: `test_fkrtl_date_window.py::test_blank_fkl30_is_missing_and_unassessed_not_a_procedure_value`.
- **Relation to the official modus:** Healthkathon defines Repeat Billing as a claim for the same case that was already billed and paid. The FKRTL sample has no billing or payment status per visit, so a candidate is a repeated-service-pattern screening signal for potential Repeat Billing, not evidence that an earlier claim was billed or paid.
- **A candidate means:** an identical recorded pattern that a reviewer should compare (separate legitimate services can match). It does **not** mean double billing. Visits on different days are out of scope (benchmark scenario `neither_next_day_repeat`).
- Tests: `test_analytics.py`, `test_fkrtl_local_source.py`, `test_detection_benchmark.py`.
- **One grouping function:** `backend/app/analytics/repeat_definitions.py::group_repeat_patterns` is used by the detector and by aggregate reports. Definitions:

  | Definition | Key | Missing key value | Amount |
  |---|---|---|---|
  | `repeat_service_v1` (core) | participant, FKL03, FKL18, FKL19, FKL30 | record ineligible | optional same-amount subset on unverified FKL47; missing excluded |
  | `repeat-service-v1` (FKRTL detector profile) | as core; FKL05/06, FKL07–09, FKL16 as context only | record ineligible (key fields only) | none |
  | `repeat-visit-exact-no-amount-v1` (former app profile, comparison only) | core + FKL05/06, FKL07–09, FKL16 | record ineligible | none |
  | `legacy_script_repeat_service` (reconciliation only) | as core | matched as literal `"<MISSING>"` | FKL47 missing/invalid counted as 0 |

- **Why 81 vs 20:** both came from `run_fkrtl_real_detection.py` on the full file with the legacy definition. 81 = groups sharing the key (all pairs: 162 rows, 81 extra rows). 20 = the subset whose FKL47 is also equal; 61 of the 81 had differing FKL47, and 81 − 61 = 20 because every group was a pair. They are not competing detector results. The legacy script also matched blank FKL30 as a value. On the FKRTL week 2024-03-04..10 the legacy definition gives 3 groups (1 same-amount) while the core definition gives 0 (15,269 records ineligible for blank FKL30), so every legacy group in that week came from blank-procedure matches. Tests: `test_repeat_definitions.py`, `test_fkrtl_data_contract.py`, `test_repeat_streaming.py`.

Of the 81 legacy groups, 67 exist only because blank FKL30 was matched as a value. Of the 153 partial groups, 14 are core groups, 105 involve blank FKL30 and 34 have present but different procedures.

The 11-field match is kept only as a secondary "same facility categories and admission diagnosis" marker within a core candidate, not as the gate: facility categories are not a facility identity, so equal values cannot confirm one facility, and requiring them hides 13 of 14 complete-key repeats. The partial signature without FKL30 stays an impact measure only and does not enter the candidate queue. No precision claim is made for either definition (no ground truth). Switching the application profile is a separate change; production code was not changed during measurement.

## Similar-claim screening (cross-participant, exploratory)

- **Product name:** "Similar-claim screening (exploratory)". It is **not** validated cloning detection.
- **Intends to find:** pairs of claims from **different** participants that agree on most compared attributes.
- **Matching rule (unchanged):** ≥ `min_compared_attributes` (9) attributes present in both records and ≥ `min_similarity` (0.8) of them equal. Only claims with the same admission date are compared (scope).
- **Blocking (engine gate, complete for the rule):** a qualifying pair has at most *k* exact-key attributes that differ or are missing in either record (`_max_bad_attributes`: k = 2 when no record carries an amount, as in FKRTL; k = 3 otherwise). The nine attributes besides the date are split into k + 1 disjoint groups, each keyed with the date (FKRTL: district + primary diagnosis + ownership; province + INA-CBG + facility type; admission diagnosis + procedure + facility class), so every qualifying pair shares at least one block. Oversized blocks are split into exact refinement buckets that omit k attributes (the amount is never an exact key), so their members are assessed once those buckets are complete. The previous three keys could not reach pairs differing only in {primary, admission diagnosis}, {district, admission diagnosis} or {province, district}, and still reported those records as assessed; oversized-block members were always unassessed. Diagnostics: `blocking_complete_for_threshold`, `max_differing_or_missing_attributes`. Tests: `test_engine_gate.py`.
- **Search allocation (Phase 3):** cross-participant pairs with enough shared attributes are the only pairs charged to the budget. Search units (blocks ≤ `max_block_size` and exact refinement buckets of oversized blocks) are processed completely, cheapest first, while they fit. Leftover budget is shared round-robin by a sorted-neighbourhood sample (members sorted by feature values; each record compared with its d-th neighbour, d = 1, 2, …). The comparison budget and the candidate cap are enforced independently.
- **Assessed means:** every unit containing the record (its blocks, or the refinement buckets of an oversized block) was completed and none of its pairs was cut by the candidate cap. Otherwise the record is unassessed.
- **Determinism:** ordering uses a seeded digest of non-identifier features, never case IDs, so the pseudonymisation key cannot change results. Records with identical features are indistinguishable under the data contract; which twin is sampled may change with input order, while counts do not. Tests: `test_near_duplicate_allocation.py`, `test_fkrtl_date_window.py`.
- **What a candidate is not:** region (FKL05/06) and facility categories (FKL07–09) are not a facility identifier, so a match **does not show the two claims came from the same facility**, and it is **not validated cloning detection**.
- **Evidence classes (utility gate):** the rule weighs every equal attribute the same, so claims sharing a common value combination (low-cardinality categories, frequent diagnosis/INA-CBG, same district and day) match each other routinely. For each qualifying pair the engine computes `match_support` = number of claims on the same date carrying every matched exact value (amount excluded), over the whole input and independent of the search budget. Support ≤ `INFORMATIVE_MAX_SUPPORT` (2: nobody but the pair shares those values) is `informative` and flags both records; support ≥ 3 is `common_attributes`: such pairs are counted in diagnostics (`common_attribute_pair_count`, `records_matched_only_on_common_attributes`) but flag nobody, and a record matched only that way stays `not_triggered`. Missing values never add support or similarity (they are neither matched nor counted as equal). Informative pairs are ordered by `expected_chance_pairs` (pairs expected by chance under an independence assumption, from same-date value frequencies), then similarity; it is an ordering key, **not a probability**, and is not used as a filter. Consequence: a copy of a claim whose matched combination is shared by ≥ 3 claims (including a template copied three or more times, or a variation of a twice-copied claim) is not flagged; it is indistinguishable from routine care on these fields. Tests: `test_engine_gate.py`, `test_additional_detectors.py`.
- **Default budget:** `max_pair_comparisons` 1,000,000 and `max_candidates` 200,000, so a 7-day FKRTL window (~378k comparisons) is assessed completely; larger windows are reported as truncated/unassessed, never negative.
- **Utility benchmark (`scripts/similar_claim_utility_benchmark.py`, ~6,650 records per seed, correlated codes, labelled routine same-day clusters, ~80 planted copies per seed of which about half copy a routine-cluster claim, hard negatives; K = 50 fixed before running; development seeds 1–5, holdout seeds 101–105 run once on the final code, aggregates in `backend/outputs/benchmarks/`).** Old = every qualifying pair (the rule); new = the engine's informative output.

Not a fraud accuracy measure.
- **Coverage on FKRTL (2024-03-04..10, 35,565 records, measured through the API workflow):** complete search, 378,284 comparisons, not truncated; 50,884 qualifying pairs, of which 6,101 informative and 44,783 common-attribute; 10,624 records (29.9%) flagged, 8,522 matched only on common attributes (not flagged). The previous release flagged every record of a qualifying pair (19,146, 53.8%) and, at its 5,000-pair default, assessed ~22%. The stored run snapshot is 40.1 MB (previously ~133 MB for a complete run), and the reopened run equals the stored one without re-running detection. 30% of a window is still not an actionable list on its own: the ranking is the usable part, and the remaining limit is the schema (no facility identifier, time of service, practitioner or claim documents), not the search.

## Checks not applicable to FKRTL

Missing values are defined once (`normalization.is_missing`): blank text and the sentinels `NA`, `N/A`, `nan`, `NaT`, `null`, `none`, `<NA>` are missing in every detector, so two missing codes never match; dates must be strict ISO dates or timestamps (a malformed string is missing, not truncated). Tests: `test_detection_correctness.py`.

Cross-participant exact pattern (needs a verified pre-verification amount), service capacity (needs facility identity, units and capacity), temporal patterns (need facility identity, service type and timestamps; the synthetic check has two parts: a repeat within a 3-day **calendar-date** window, and clusters at the same **minute** of a synthetic timestamp; FKRTL dates carry no hours or minutes) and supporting-evidence completeness (needs an evidence inventory) are declared not applicable by the FKRTL provider. Test: `test_coverage_correctness.py::test_configured_fkrtl_run_reports_unsupported_checks_as_not_applicable`.

## ML unusual-claim ranking

- **Model:** Isolation Forest (scikit-learn) on frequency-encoded verified codes, code-pair frequencies, length-of-stay deviation per INA-CBG, visits per participant within the run, and diagnosis change. No identifiers or amounts are features.
- **Determinism (Phase 3):** the model is fitted on rows in canonical (sorted feature-vector) order, so scores do not depend on input order or the pseudonymisation key. Ranks are competition ranks: equal scores (at reported precision) share a rank and report `tie_count`; list order among ties is not meaningful. Tests: `test_ml_ranking.py`.
- **What the score is not:** it is relative to one run, not comparable across runs, **not a fraud probability**, and **not a facility audit priority**. It does not change the rule index, action lanes or facility priority (`test_ml_ranking.py::test_ml_ranking_does_not_change_rule_risk_or_audit_priority`). - **Benchmark evidence (v2, 10 seeds):** Precision@10/25/50 averaged 0.47/0.33/0.26 against a random expectation of 0.06 and a rule-flag ranking expectation of ~0.07. The gain comes almost entirely from compound anomalies (repeat pair + code mismatch + long stay, median rank ~9). Single-dimension targets rank poorly: code-family mismatch median rank ~93, 20–30 day stays ~224, frequent visitors ~221 of 864, even though the stay feature is extreme. All 12 benign rare-code records reach the top 50 in every seed (median rank ~15). The ranking mainly rewards code rarity. Output is identical under row permutations in all seeds. Low overlap with rule flags alone does not establish value.

- **FKRTL runs: offline-trained model `cir-iforest-fkrtl-v2` (`app/analytics/ml_model.py`).** Trained by `python -m scripts.train_ml_model --date-from 2024-02-05 --date-to 2024-03-03` on 126,871 records of the configured FKRTL source (classification `bpjs_sample`), read through the same reader and adapter as a run; held-out week 2024-03-04..10 (35,565 records). Artifact `backend/models/cir-iforest-fkrtl-v2/` (`model.joblib` 5.4 MB, `reference.json` with code and code-pair counts ≥ 5 only, peer duration medians/MADs, feature and score quantiles; `manifest.json` with SHA-256 checked before unpickling). A run loads it and scores records; nothing is refitted. Synthetic CSV runs keep the per-run ranking above.
- **Features (one shared pipeline for training and inference):** conditional frequency in training of four code pairs (primary diagnosis→INA-CBG, INA-CBG→procedure, admission→primary diagnosis, facility class→INA-CBG); length-of-stay deviation from the training median of the same INA-CBG and class of care (robust, MAD-scaled; falls back to INA-CBG, then global, below 30 stays); log visits by the same pseudonymous participant in the same ISO week (grouping only); admission diagnosis differs from primary. Excluded: identifiers, HMAC values, all amounts (FKL47 and FKL48), region and facility category frequencies, and single-code rarity. Eligibility (admission date, primary diagnosis, INA-CBG present) is checked before scoring; ineligible records are `not_assessed` with a reason, never a low score. Rare or unseen values share one frequency (count 2.5).
- **Output:** `anomaly_score` (higher = more unusual), `reference_percentile` against the training scores (comparable across runs with the same artifact), in-run rank, and up to three `supporting_signals` (features at or above the training 95th percentile). Signals are not a model explanation; no SHAP or attribution is computed.
- **Correction (one, evidence-driven):** v1 also scored single-code rarity. On the held-out week 187 of its top 200 were driven by a rare INA-CBG alone, and on injections (seeds 1–3) it found 30–35 injected records in the top 200 against 59–64 for the transparent baseline. v2 drops those features. The correction was chosen on seeds 1–3 and confirmed once on fresh seeds 11–13.
- **Held-out real data (unlabeled, no accuracy claimed):** all 35,565 records scored, 0 not assessed; 1.07% score above the training 99th percentile (expected ~1% if the week resembles training); top 200 signals: facility class→INA-CBG combination 169, duration 161, diagnosis→INA-CBG 46, admission→primary diagnosis 44, weekly visits 19. Inference 8.7 s, peak traced memory 38 MB; training read 145 s, fit 46 s, peak ~400 MB.
- **Controlled injections (synthetic changes to copies of held-out records, 50 per type and seed, K fixed at 200 and 500 before running; the labels are the injections, not fraud):**

  | Type | AUC v1 (seeds 1–3) | AUC v2 (1–3 / fresh 11–13) | Single-feature AUC | v2 top-200 hits | Baseline top-200 | Rule/screen flagged |
  |---|---|---|---|---|---|---|
  | INA-CBG from another case-mix group | 0.93–0.94 | 0.93–0.94 / 0.93–0.94 | 0.86–0.92 | 4–7 | 5–9 | similar-claim 8–12 |

  Top-500 hits for all injected: v2 92–111, transparent baseline (highest single-feature training percentile, no model) 108–120. The repeat rule and duration screen flag their own patterns far more reliably, and the single relevant feature separates each type better than the model. Isolation Forest scores saturate at the edge of the training range, so a far more extreme value does not score higher than the most extreme training records.
- **Why Isolation Forest, not Gradient Boosting:** the proposal compared weighted rules with Gradient Boosting. Gradient Boosting is supervised and needs fraud labels; the FKRTL sample has none, and on synthetic labels the supervised models lost to the transparent rules and failed robustness checks (subtypes withheld from training were not found; see `demo-alignment-brief.md`). They remain experimental comparisons outside this release. The only model that can be trained honestly on unlabeled actual records is an unsupervised one, so the active model is Isolation Forest. It is a separate ML signal: it is not combined with the rule index, does not change action lanes or priority, and is never a fraud verdict.
- **Lifecycle:** the artifact is produced only by the training command from the configured local source; the application never trains or accepts a model from a request. Before unpickling it verifies model version, feature-pipeline version, the scikit-learn version that wrote it (pinned in `requirements.txt`), and SHA-256 checksums; startup reports a path-free status (`ml_model` on the FKRTL source status, warning log), and a missing or mismatched artifact leaves ML `unavailable` while the rules run. The checksum proves integrity, not origin: only artifacts built locally or shipped in this repository are trusted.
- **Conclusion:** the model is active in the FKRTL run path and separates synthetic inconsistencies from unchanged records, but it is no better than a transparent baseline and does not replace the rules. It is an exploratory ordering aid, not a validated fraud detector. Tests: `test_ml_model.py`; evaluation `python -m scripts.evaluate_ml_model --seeds 1-3 --save`.

## Unusual duration relative to comparable claims (exploratory)

- **Intends to find:** admission-to-discharge spans that are long compared with similar claims, as a prompt for human review. Related official modus: #12 prolonged length of stay (extension not justified by medical indication); the screen cannot judge medical indication.
- **Fields:** FKL03 admission date, FKL04 discharge date, FKL19 INA-CBG and FKL13 class of care (dictionary p. 20: "kelas rawat saat peserta mengakses pelayanan kesehatan di FKRTL"). No identifiers, facility categories, or amounts are used; the participant token is only compared to count exact copies once.
- **Method (`los-peer-p99-v1`, declared before benchmarking):** span = calendar days between the dates (date-only, no hours). Peer group = same INA-CBG and class of care in the analysed window. Threshold = nearest-rank 99th percentile, the value at position ceil(0.99·n) of the sorted peer spans. A candidate has a span strictly above the threshold and at least 1 day; ties at the threshold and same-day stays are never flagged. Minimum peer support is 100, because below that the nearest-rank 99th percentile equals the group maximum.
- **Unassessed reasons:** missing date, invalid date, discharge before admission, missing INA-CBG or class, and too few comparable claims.
- **What a candidate is not:** statistical unusualness is not evidence of fraud and does not show the stay was unjustified; complications, discharge status and hours are not considered. The threshold is a screening choice, not a clinical or BPJS limit. Results are window-relative.
- **Separation:** standalone section in Analysis Details and Case Review; it does not feed the rule index, action lanes, facility priority or the ML ranking (`test_length_of_stay.py::test_duration_screen_does_not_change_rule_risk_or_priority`). Tests: `test_length_of_stay.py`, `test_detection_benchmark.py`.
- **Synthetic evidence (10 seeds, 1,972 records each):** planted extreme spans recall 0.9–1.0 (mean 0.94), 8.3–9.3 candidates per 1,000 assessed, 0 alerts on ordinary-duration controls, ~1% of a natural 5–9 day tail flagged, and 92.5% of legitimate long stays flagged (expected: they are statistically identical; this is not a fraud false positive). Misses occur when long stays exceed 1% of a peer group, which lifts the 99th percentile (masking). The unchanged ML ranking placed none of these targets in its top 17 and about half in its top 50, while ranking ordinary rare-code claims higher.
- **FKRTL week 2024-03-04..10:** 29,903 of 35,565 records assessed (all unassessed records had too few comparable claims: 840 peer groups below support, 22 assessed); 1 candidate (0.03 per 1,000). A one-week window leaves most variable-duration INA-CBG groups below support.

## Drug/device claims

No drug/device detector exists in this release. The proposal phrase "Klaim Fiktif Obat/Alkes" matches official facility modus #17 (drugs, devices or procedures billed but not given to the patient). It is distinct from #7/#19 *inflated bills* (cost higher than actual) and #18 (fewer drugs handed over than billed); drug/device misuse is a participant-category modus. The four-mode benchmark rows for drug/device above are synthetic-only experiments; any future detector must name its official modus and needs item lines, quantities, billed item prices and dispensing/handover records linked to the visit.

## Rule index and facility priority

The rule index is withheld (`insufficient_assessed_indicators`) when fewer than 3 checks assessed a claim; on FKRTL only 2 apply, so it is always withheld there. Facility audit priority requires a verified facility identifier and amount and is not assessable on FKRTL. The proposal formula (risk × claim value × audit effort) is a design concept: FKL48 is post-verification and never read, and FKL47 is not used for monetary priority until its semantics and pre-verification availability are confirmed. Green/yellow/red lane bounds (1/3, 2/3) are provisional CIR recommendations for synthetic runs, not BPJS policy. No gradient boosting model or SHAP explanation is part of this release; explanations are rule reason trails.

## Synthetic benchmark (v2)

`python -m scripts.detection_benchmark --seeds 1-10` generates labelled scenarios and evaluates the repeat rule, similar-claim screening and ML ranking independently, with exact random and rule-flag baselines. Ground truth is separate from the records: every record has an expected state per method and every planted pair has its own label. Similar-claim precision uses every returned candidate pair as the denominator; a true positive is a returned pair that is exactly a labelled target pair. Detector and model settings were not tuned on these seeds. It reports synthetic-benchmark behaviour only and is not evidence of real-world fraud detection. Tests: `test_detection_benchmark.py`.

## Four-mode synthetic benchmark (v1)

`python -m scripts.mode_benchmark --seeds 1-10 --aggregate-only [--save]` (module `backend/scripts/mode_benchmark.py`; it reuses the code tables, ID and statistics helpers of `detection_benchmark.py`). Saved output goes to `backend/outputs/benchmarks/` (ignored by Git) and holds counts only.

- **Shared contract:** every record has exactly `CANONICAL_FEATURE_FIELDS` and passes `canonicalize_feature_dataset`; amounts are absent as in FKRTL. `SYNTHETIC_ONLY_FIELDS` are the canonical fields the FKRTL adapter always leaves `None` (facility ID, service type, evidence inventory, capacity, timestamp); they are populated for simulation only. Item lines, dispensing lines and the execution-log day match are not canonical: they live in a separate sidecar read only by the naive baselines. Labels live in `truth` and never reach records, the sidecar or a detector.
- **Real-data input:** one aggregate, the whole-file FKL30 blank rate (0.4169), applied per episode to every scenario alike. Facility pools (60 category tuples over 30 districts in 10 provinces, each tuple shared by two synthetic facilities, so categories are never an identity), code tables and the 12% evidence-sync delay are synthetic assumptions. The district/province pool was enlarged once after a first draft with 5 districts made most background claims near-duplicates; detectors were not tuned.
- **Design:** per seed 1,500 background claims (+ legitimate revisits) and 12 instances of each scenario; 10 seeds; 20,115 records over the 10 datasets (2,006–2,014 per seed). The unit of evaluation is the record (claim).
- **Cohort per mode:** that mode's positives and controls plus all background records; other modes' records are excluded (counted as `excluded_other_mode_records`, flags on them reported separately). Pooled over 10 seeds: repeat 17,595 cohort + 2,520 excluded; cloning 17,835 + 2,280; phantom 16,875 + 3,240; drug/device 16,995 + 3,120.
- **Coverage states (disjoint, per method):** *assessed* = evaluated; *unassessed* = the method applies but a required field/value is missing or invalid, the evidence inventory is not synchronised, or a bounded search did not reach the record (detector `ineligible`/`unassessed` outputs; blank FKL30 for repeat; missing amount for the cross-participant exact pattern, which the FKRTL runtime instead declares not applicable); *not applicable* = no rule for the record (evidence check without a rule for the service type; naive phantom/drug baselines outside their service types). For every seed, mode and method `positives = assessed + unassessed + not applicable`, the same for negatives, `TP + FN = assessed positives`, `FP + TN = assessed negatives`, `positives + negatives = cohort`, `cohort + excluded = dataset`, and every flagged record is assessed; `reconcile()` raises otherwise (`test_mode_benchmark.py`).
- **Denominators:** precision `TP/(TP+FP)`; recall on assessed `TP/(TP+FN)`; recall on all positives `TP/positives`; FPR `FP/(FP+TN)`; flagged records per 1,000 *cohort* records and per 1,000 *assessed* records are reported separately; cohort prevalence `positives/cohort`; assessed prevalence `assessed positives/assessed records` = expected precision of random flagging among the records a method assesses. Candidate units are counted separately from flagged records: groups (repeat, exact pattern, naive repeat/cloning), pairs (near-duplicate) or records (evidence, ML top K, naive phantom/drug).

Methods that assess only part of the cohort must be compared with their assessed prevalence, not the cohort prevalence; flagged-per-1,000 values are comparable only within one denominator. The cross-participant exact pattern assesses no record in any mode (all unassessed: amount missing), so its precision, recall and FPR are undefined.

Per scenario (rate on assessed records, mean of 10 seeds):
- **Repeat:** `repeat-service-v1` flags 1.0 of exact and context-varied resubmissions, 0 of different-procedure and next-day controls, and 1.0 of legitimate same-key referrals (its false positives); the 11-field profile flags 0 context-varied resubmissions and 0 referrals. Blank FKL30 pairs (~40%) are unassessed under both and never form a partial match. Which profile is "more precise" depends on the assumed referral share, which real data cannot tell; the profile choice rests on the whole-file reconciliation, not on this benchmark.
- **Cloning:** the near-duplicate screen flags 1.0 of admission/care-class/procedure variants but only 0.39 of one-day-shifted copies, and 1.0 of both control kinds (routine same-facility claims and claims at another facility with identical categories). It also flags ~33% of background claims, mainly because the reused 30-diagnosis code table makes exact same-day matches common; this rate depends on the code-space size. Even the facility-aware baseline (synthetic facility ID) cannot separate copies from routine same-facility claims.
- **Phantom:** the evidence check flags 1.0 of claims whose execution record is absent and 0 of claims whose record exists for another day (it checks presence only); records filed under another document type are false positives (1.0 of assessed); not-yet-synchronised inventories are unassessed (1.0), not negative. Absent (flagged), not synchronised (unassessed) and no rule (not applicable) are reported separately in `evidence_states`.
- **Drug/device:** with the scenario rule the claim-level check flags 1.0 of claims with no dispensing record and 0 of claims where only one of several items is undispensed (it cannot see item lines); it raises no false positive on late, unit-difference or substitution controls. The item-level naive baseline finds every positive but flags every control.
- **Other detectors:** the repeat profiles flag nothing in cloning, phantom or drug scenarios; the cross-participant exact pattern assesses nothing (needs an amount); the ML ranking at K = positives stays close to the random rate (precision 0.005–0.04 against prevalence 0.014–0.054): it does not target these modes.
- **Balance:** the FKL30 blank rate is 0.39–0.43 for positives and negatives in every mode. Not-synchronised evidence is more frequent in controls by construction (the sync-pending controls), which makes controls unassessed, not positives easier.
- **Limits:** labels are simulation contracts, not fraud labels; synthetic-only attributes do not exist in the FKRTL sample; results do not transfer to BPJS data, which has no ground truth. Tests: `test_mode_benchmark.py`.

## Component status

| Component | Status | Reason |
|---|---|---|
| Same-participant repeat visit (FKRTL profile `repeat-service-v1`) | Operational review signal, narrow scope | Recall 1.0 on assessed synthetic positives; legitimate same-key referrals are its known false positives. 41.7% of the whole FKRTL file is unassessed (blank FKL30, meaning unresolved); 14 complete-key groups in the whole file. |
| Similar-claim screening (cross-participant) | Exploratory signal only | Complete on a 7-day FKRTL window; only pairs not explained by a common value combination flag records, ranked by chance expectation (synthetic precision@50 0.16–0.30 vs 0.00–0.04 for the plain rule, holdout-confirmed), but candidate precision stays ~1% and copies of common claims are not separable without facility identity or documents. |
| Unusual duration relative to comparable claims | Exploratory signal only | Explainable and well-behaved on synthetic data, but very low support and yield in a one-week FKRTL window; a long stay is not evidence of fraud. |
| ML unusual-claim ranking | Exploratory signal only; active in FKRTL runs | FKRTL runs score with the offline-trained artifact `cir-iforest-fkrtl-v2` (trained on 2024-02-05..03-03, held-out week 2024-03-04..10). On synthetic injections into held-out records it separates changed from unchanged claims (AUC 0.88) but is not better than a transparent single-feature baseline, and the repeat rule and duration screen find their own patterns more reliably. Synthetic CSV runs keep the per-run ranking, which earlier evaluations found driven by code rarity. No fraud accuracy is claimed. |
| Capacity, temporal, evidence completeness, cross-participant exact pattern | Deferred for FKRTL | Required fields are absent from the source (not applicable). |
| Facility audit priority | Deferred | No verified facility identifier or pre-verification amount. |
